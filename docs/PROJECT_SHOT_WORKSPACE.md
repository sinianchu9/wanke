# Wanke Project / Shot 作品项目层

## 1. 目的

Wanke 已经具备 AI 视频生成、批量候选、继续创作、原生延长、整条视频编辑、主体卡和任务中心。如果所有结果仍只堆在 Job 列表里，作品一复杂就很难判断：

- 这些任务属于哪个作品；
- 这是哪个镜头的候选；
- 哪一个版本最终采用；
- 某个编辑版 / 延长版是哪个镜头的后续；
- 一个项目会长期使用哪些人物和产品。

Project / Shot 层解决的是**生产组织关系**，不是新增生成模型。

## 2. 核心关系

```text
Project 作品项目
├─ Project Subjects 项目主体
│  ├─ 人物卡
│  └─ 产品卡
│
├─ Shot 01
│  ├─ Job A · 候选
│  ├─ Job B · 候选 ✓采用
│  └─ Job B 的延长 / 编辑 / 重试子任务
│
├─ Shot 02
│  ├─ Job C
│  └─ Job D ✓采用
│
└─ 每个 Shot 的采用版本
   = 项目的最终镜头清单
```

## 3. 边界

### Project

Project 表示一个作品，例如：

- 智能手环夏季广告；
- 品牌女装 30 秒短片；
- 咖啡店剧情短视频。

Project 负责组织，不直接提交 Provider。

### Shot

Shot 表示一个明确镜头目标，例如：

- Shot 01 · 产品正面特写；
- Shot 02 · 模特佩戴行走；
- Shot 03 · 夜景结束镜头。

一个 Shot 可以有很多候选 Job，但最多只能标记一个采用版本。

### Job

Job 仍然是实际执行单元。项目层不会把多个任务合并成一个假任务。

### Subject Card

项目可以绑定人物 / 产品主体卡，用来记录“这个作品会使用哪些主体”。

**项目主体不会自动注入每一个 Shot 的生成请求。**

具体某个镜头要使用哪些人物、产品，仍然在 AI 视频的“保持人物 / 产品一致”模式中明确选择。这样避免项目组织层偷偷改变模型输入。

## 4. 数据删除规则

### 删除 Project

只删除：

- Project；
- Project 下的 Shot；
- Shot 与 Job 的组织关系；
- Project 与主体卡的组织关系。

**不会删除 Job，不会删除生成结果，不会删除主体卡。**

### 删除 Shot

只删除该 Shot 和归类关系，不删除 Job。

### 删除 Job

`shot_jobs.job_id` 使用外键级联：Job 删除后会自动从 Shot 候选中移除。

如果这个 Job 正好是 Shot 的采用版本，`selected_job_id` 会自动置空。

### 删除主体卡

项目与该主体的关联会自动删除，不影响项目本身。

## 5. 子任务自动继承 Shot

这是项目层最重要的闭环之一。

当一个 Job 已经属于某个 Shot：

```text
Shot 01
  ↓
原始生成 Job
  ↓
失败重试 / 类似版本 / 继续创作 / 视频延长 / 视频编辑
```

这些以 `parentJobId` 创建的子任务，会在 `createJob` 层自动继承父任务的 Shot。

因此各功能不需要重复写“把子任务重新放回项目”的代码。

## 6. 从 Shot 发起创作

操作：

```text
作品项目
  ↓
打开某个 Shot
  ↓
点击“在此镜头创作”
  ↓
进入 AI 视频
  ↓
页面显示当前 Project / Shot 上下文
  ↓
提交任务
```

单任务会直接进入 Shot。

批量 2–4 个版本时，每个独立 Job 都会进入同一个 Shot。

当前 Shot 上下文只自动作用于 **AI 视频入口**。视频拆解、脚本等中间工作流不会因为用户之前选过 Shot 就自动混入镜头候选；已有成熟视频任务仍可以在项目页手动加入 Shot。

## 7. 采用版本

项目层只有满足以下条件的 Job 才能设为“采用”：

- Job 状态为 `succeeded`；
- 至少有一个真实视频输出；
- Job 当前属于这个 Shot。

JSON、字幕、分析结果或没有视频输出的任务可以作为组织记录加入 Shot，但不能被标记为最终采用镜头。

每个 Shot 只能有一个 `selected_job_id`。

切换采用版本不会删除旧候选。

## 8. 整理历史任务

旧任务不需要重新生成。

在 Shot 中可以选择“加入已有任务”，把尚未归类的历史 Job 放进当前 Shot。

这样上线 Project / Shot 以后，过去已经生成的内容也可以逐步整理进项目。

## 9. 示例：智能手环广告

```text
Project：黑色智能手环夏季广告

项目主体：
- 女主角 A
- 黑色智能手环

Shot 01 · 产品特写
目标：深色桌面，镜头缓慢环绕产品
候选：
- 版本 1
- 版本 2 ✓采用
- 版本 3

Shot 02 · 佩戴镜头
目标：女主角佩戴手环在街道行走
候选：
- 原始生成
- 视频编辑版 ✓采用

Shot 03 · 结尾
目标：人物停下抬腕，镜头推近屏幕
候选：
- 原始 5 秒
- 延长到 10 秒 ✓采用
```

最终 Project 已经天然拥有三条定稿镜头，为下一阶段接时间线、镜头排序、拼接成片提供稳定数据基础。

## 10. 为什么现在不直接做时间线

当前阶段先保证：

1. 项目关系正确；
2. Shot 关系正确；
3. 候选版本不会混乱；
4. 子任务血缘能自动继承；
5. 每个 Shot 有明确采用版本。

如果这些基础关系没有先稳定，直接做时间线只会把 Job 列表的混乱搬到另一个 UI。

因此当前 Project / Shot 是时间线之前的必要生产层。

## 11. 当前不做

第一阶段明确不做：

- 多人协作权限；
- 云端团队项目；
- Shot 时间码；
- NLE 多轨时间线；
- 自动拼接最终成片；
- 项目级自动 Prompt 注入；
- 项目主体自动注入所有镜头；
- 自动替用户选择最终版本。

这些能力以后可以在当前数据关系上继续增加。

## 12. 验收标准

- [x] Project 持久化；
- [x] Shot 持久化；
- [x] Project 可关联主体卡；
- [x] Shot 可包含多个真实 Job；
- [x] 一个 Job 最多属于一个 Shot；
- [x] Shot 最多一个采用 Job；
- [x] 只有成功且有视频输出的 Job 可采用；
- [x] 从 Shot 发起单任务自动归类；
- [x] 从 Shot 发起批量版本自动归类；
- [x] 子任务自动继承父 Job 的 Shot；
- [x] 可整理未归类历史任务；
- [x] 删除 Project / Shot 不删除 Job；
- [x] 删除 Job 自动清理 Shot 关系；
- [x] 页面内包含边界说明和操作演示。
