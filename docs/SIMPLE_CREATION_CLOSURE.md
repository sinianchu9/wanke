# Wanke 简单创作闭环 / Simple Creation Closure

## 目标

简单模式不是削弱 Wanke，而是让普通用户不用理解工程结构也能完成完整业务闭环：

```text
第一次打开
  ↓
配置一次视频服务（仅首次）
  ↓
给主体 / 一张图片
  ↓
一句话描述
  ↓
自动规划并生成镜头
  ↓
失败原地重试
  ↓
不满意再生成一个
  ↓
多个版本自己选择
  ↓
成功结果自动保存
  ↓
一键最终成片
  ↓
以后重新打开仍能继续
```

高级创作、Project / Shot、Provider、媒体规格、转场、声音、字幕和 FFmpeg 能力仍全部存在，但不再是普通用户完成一次视频的必经步骤。

---

## 1. 第一次使用

### 1.1 视频服务未配置

快速创作先读取统一 Settings 状态。

未配置时：

- 不创建 Project；
- 不创建必然失败的 Job；
- 页面显示“去配置”；
- 配置完成后直接返回快速创作。

服务状态正在加载时显示“正在检查视频服务”，不会把加载中误报成未配置。

### 1.2 设置来源一致

百炼 / 万镜一刻均读取统一运行时 Settings：

```text
UI 保存设置
  ↓
SQLite settings
  ↓
运行时配置
  ↓
生成 / 素材 / 上传 / 扩展工作流
```

本次复审修正了素材 API 仍只检查 `.env` 的旧逻辑，因此通过 UI 设置的 Yike AccessKey 现在也会被素材登记层正确识别。

---

## 2. 主体 / 图片输入

快速创作不要求提前建立主体卡，也不要求提前整理素材库。

### 产品广告

二选一：

1. 选择以前保存的产品主体；
2. 本次直接给一张产品图片。

### 人物短视频

二选一：

1. 选择以前保存的人物主体；
2. 本次直接给一张人物图片。

### 图片变视频

直接给一张图片。

### 图片来源

普通用户只看到三种业务选择：

- 已有图片；
- 公网 HTTP/HTTPS 图片直链；
- 电脑里的 JPG / PNG / WEBP（10MB 内）。

电脑本地图片的底层路线由系统自动决定：

#### 百炼直连可用

```text
电脑图片
  ↓
/api/video-inputs
  ↓
wanke-input:// 短引用
  ↓
Job 保存短引用
  ↓
提交前转 Base64
  ↓
Model Studio
```

临时图片不会被塞进数据库大字段。只要仍有 Job 引用它，就不会被误删。

#### 当前使用 Yike 上传能力

```text
电脑图片
  ↓
获取上传凭证
  ↓
浏览器上传到服务端指定 OSS
  ↓
自动登记到 Wanke 素材库
  ↓
快速创作直接使用
```

用户仍然只点击同一个“选择电脑里的图片”，不需要理解两条技术路线。

如果当前服务既不能临时直传，也没有扩展上传能力，才退回到“已有图片 / 公网图片链接”。

---

## 3. 创建 Project 前的预检

“配置存在”不等于“当前图片一定能被当前线路读取”。

因此快速创作在创建 Project 之前还会对第一个代表镜头执行：

```text
图片 / 主体
  ↓
prepareJobInput
  ↓
生成 schema 校验
  ↓
当前 Provider 兼容性检查
```

同一个快速作品的所有 Shot 使用同一组参考素材与同一种生成方式，所以代表镜头可以覆盖素材兼容性边界。

如果素材无法被当前固定线路读取：

- 直接返回业务提示；
- 不创建 Project；
- 不创建失败 Job；
- 用户换图或调整服务后重试。

真正 API Key 权限、模型权限、账户额度等仍只能由真实生成请求验证，不能伪造“零成本测试已通过”。

---

## 4. 快速创作提交

用户只回答：

1. 做什么；
2. 主体 / 图片是什么；
3. 一句话要求；
4. 发到哪里；
5. 大约多长。

系统自动：

```text
需求
  ↓
Quick Creation Plan
  ↓
Project
  ↓
1–4 个 Shot
  ↓
每个 Shot 一个独立 video_generation Job
  ↓
现有 prepareJobInput
  ↓
现有 Provider Router
```

没有第二套“简单生成引擎”。

### 时长规则

```text
5 秒  → [5]
10 秒 → [5, 5]
15 秒 → [5, 5, 5]
30 秒 → [10, 10, 5, 5]
```

多镜头快速作品默认使用 0.5 秒自然淡化，因此 UI 使用“大约时长”，不虚假承诺最终时长精确到毫秒。

---

## 5. 我的作品：完整恢复状态

### 生成中

显示“生成中”。

如果已经有一个成功版本，但用户主动要求“再生成一个版本”：

- 旧版本仍可预览；
- 新版本显示生成中；
- 最终成片等待新候选完成；
- 不会偷偷忽略用户刚请求的新候选。

### 生成失败

页面显示实际失败原因（过长信息会截短），并提供：

> 重试这个镜头

retry 子任务通过现有 `parentJobId` 机制自动继承 Shot。

### 一个成功版本

直接预览。

如果用户没有显式选择采用版本，最终成片可以自动采用这个唯一成功版本。

同时可以：

> 再生成一个版本

调用现有 `similar`，原版本不会被覆盖。

### 多个成功版本

简单页直接展示候选视频：

```text
版本 1 [预览] [选这个]
版本 2 [预览] [选这个]
```

服务端 `selectShotJob()` 再次验证：

- Job 属于这个 Shot；
- Job 已 succeeded；
- Job 有视频输出。

选择完成后仍可随时换另一个成功版本。

简单模式绝不自动猜多个候选里的“最佳版本”。

### 操作失败

重试、再生成、选版本的错误直接显示在镜头工作区顶部，而不是藏在页面底部的最终成片区域。

## 6. 成功结果自动保存

Provider 的结果 URL 可能过期，所以快速创作 Job 在轮询到 `succeeded` 后会尽力自动本机归档。

```text
远端 Job succeeded
  ↓
确认属于 quick creation
  ↓
最多 2 路并发归档
  ↓
成功 → archivedFile 写回 Job
失败 → Job 仍是 succeeded，quickArchive=pending
```

归档失败不能把真实生成成功的任务改成 failed。

### 并发安全

两个浏览器标签页可能同时触发 refresh / archive。

归档路径会在失败时重新读取最新 Job：

- 如果另一个请求已经保存成功，当前请求改认 `saved`；
- 不允许过期请求把已成功状态重新覆盖为 `pending`。

Studio 自身的 6 秒自动轮询也有 in-flight guard，上一次 refresh / archive 未结束不会再启动下一轮。

## 7. 最终视频

“生成最终视频”执行：

```text
检查所有 Shot
  ↓
唯一成功版本 → 自动采用
多个成功版本 → 要求用户先选
  ↓
检查采用视频本机归档
未归档 → 再尝试保存
  ↓
assembleProject()
  ↓
媒体规格统一
  ↓
项目转场
  ↓
声音 / BGM / LUFS
  ↓
字幕
  ↓
最终 MP4
```

不会建立第二套简化 FFmpeg 流程。

### 自动归档与成片同时发生

最终成片的补归档也会重新读取 Job 状态。

如果后台归档恰好同时完成，不会误报归档失败。

### 云端链接已经过期

如果成功结果一直没有保存下来，最终成片给普通用户的恢复提示是：

- 稍后再次点击“生成最终视频”；
- 如果持续失败，云端结果可能已经过期；
- 在对应镜头点击“再生成一个版本”。

### ffmpeg / ffprobe 未准备

普通用户不会看到长串系统工具错误，而会得到：

> 镜头已经准备好，但服务器还没有准备好最终成片能力。

已经生成和保存的镜头不丢失。

---

## 8. 历史成片与当前状态

重新进入“我的作品”会读取最近一次 Project assembly 并直接提供播放。

但“有历史成片”不等于“历史成片反映当前选择”。

系统比较：

```text
assembly.createdAt
vs
project.updatedAt
```

如果之后发生过：

- 换候选；
- 新增候选；
- 修改镜头；
- 修改 Project 声音 / 字幕 / 转场等设置；

旧 MP4 仍可播放，但页面明确标注：

> 这是之前生成的成片；要反映当前选择请重新生成最终视频。

不会把历史输出冒充当前输出。

## 9. 简单与高级模式边界

### 简单模式负责

- 第一次输入；
- 本机图片自动适配上传路线；
- 自动拆镜；
- 生成进度；
- 失败原因；
- 失败重试；
- 再生成候选；
- 选择 / 更换候选；
- 成功结果自动保存；
- 最终成片；
- 历史成片恢复；
- 历史成片是否已经过期于当前作品状态的判断。

### 高级模式负责

- 精确 Prompt / Recipe；
- 复杂多参考；
- 手工建立 / 修改 Shot；
- Shot 排序；
- 视频延长 / 编辑；
- 媒体规格诊断；
- 转场参数；
- BGM / LUFS；
- SRT；
- 成片历史管理；
- Provider / 模型 / API 细节。

原则：

> 高级模式用于“我要更细控制”，不能用于修补简单模式本来就应该处理的日常业务缺口。

## 10. 使用演示

### A. 第一次做产品广告

```text
快速创作
→ 产品广告
→ 选择电脑里的手环图片
→ “突出循环震动提醒，科技感，动作克制”
→ 抖音
→ 10 秒
→ 开始创作
```

如果当前是百炼直连，图片临时直传；如果当前主要依赖 Yike，图片自动上传并登记。用户不需要选择路线。

系统建立：

```text
Project
├─ 开场吸引 5s
└─ 产品展示 5s
```

两个任务完成后尽力自动保存，用户在“我的作品”直接预览并生成最终视频。

### B. 一个镜头失败

```text
Shot 01 ✓
Shot 02 需要重试
```

页面显示失败原因。

用户点击：

```text
重试这个镜头
```

新 Job 自动留在 Shot 02。

### C. 一个版本不够好

```text
Shot 01 已完成
→ 再生成一个版本
```

新候选完成后：

```text
版本 1 [预览] [选这个]
版本 2 [预览] [选这个]
```

用户明确选择后继续成片。

### D. 换版本后已有旧成片

```text
昨天：版本 1 → 生成 final.mp4
今天：改选版本 2
```

页面继续允许播放昨天的 MP4，但标记为旧成片，并提示重新生成才能反映版本 2。

### E. 几天后回来

如果镜头已自动归档：

- 不依赖原 Provider URL；
- 可以继续选版本；
- 可以重新生成最终视频；
- 最近成片仍能找回；
- 是否对应当前 Project 状态一目了然。
